# Old Tree Cafe — website

A single-page website for Old Tree Cafe, Kandlakoya, Kompally, Hyderabad.

Static by design: no server, no database, no build step and no dependencies.
The whole site is three hand-written files plus photos — about 99 KB of code —
which means it can be hosted free, loads instantly, and has essentially no
attack surface.

---

## 1. What each file does

```
OTC/
├── index.html          the page itself — all the words and the structure
├── robots.txt          tells crawlers what to index
├── sitemap.xml         the one-line map of the site, for Search Console
├── README.md           this file
│
├── code/               everything the browser runs
│   ├── styles.css      every colour, font, size and layout rule
│   ├── script.js       the menu data, and everything the page does
│   ├── build.sh        optional, squashes the three files into one
│   ├── demo.html       generated by build.sh — one standalone file
│   └── artifact.html   generated by build.sh — the same, minus the wrapper
│
└── images/             every photo
    ├── og.jpg          1200x630, the card messaging apps show for the link
    ├── splash.avif     the photo behind the OTC letters
    └── …               the rest, named for the slot each one fills
```

`index.html` stays at the top on its own, and it has to. Every web server,
asked for the site root, looks for `index.html` in the folder it was handed.
Put it inside `code/` and visitors get a blank page. The other two moved down
into `code/`, and `index.html` points at them as `code/styles.css` and
`code/script.js` — that is the only reason those two paths look the way they do.

### The three that matter

| File | Language | Job | House analogy |
|---|---|---|---|
| `index.html` | HTML | **What is on the page** | The walls and rooms |
| `code/styles.css` | CSS | **What it looks like** | Paint, furniture, lighting |
| `code/script.js` | JavaScript | **What it does** | Light switches and doorbells |

All three could live in one file. They are kept apart so that changing a colour
means opening one file and changing one line, without going near the words on
the page.

### `index.html` — the page

Split into sections, each marked with a comment:

- **`<head>`** — not visible. The page title, the description search engines
  show under the link, the `og:` tags that decide the preview card when the link
  is shared, and the two `<link>` lines pulling in the fonts and
  `code/styles.css`.
- **header** — sticky bar: logo, nav links, open/closed pill, WhatsApp button.
- **splash** — the first screen. Full-height, the OTC letters over
  `images/splash.avif` behind a sheet of frosted glass. The photo drifts a
  little with the pointer (script.js §13). To use footage instead, swap the
  `<img class="splash-photo">` for a
  `<video class="splash-photo" autoplay muted loop playsinline>` — the CSS is
  written against the class, not the tag, so nothing else moves.
- **hero** — headline, one paragraph, two buttons, three facts.
- **garden** — the six things that make the place different.
- **menu** — an empty `<div>`. `code/script.js` fills it in.
- **gallery** — fifteen photos, click any one for the lightbox.
- **visit** — address, phone, directions button, opening-hours table.
- **footer** — the contact details again, for people who scroll to the bottom
  looking for them.

### `code/styles.css` — the look

The top block is the important one:

```css
:root {
  --bg:     #EEF1E6;
  --ink:    #1B2A21;
  --accent: #A96A12;
  ...
}
```

Those are CSS custom properties. Every colour in the rest of the file refers to
one of these names instead of a hex code, so changing `--accent` once changes
every button, heading underline and link with it.

Underneath is a second, near-identical block wrapped in
`@media (prefers-color-scheme: dark)`. If the visitor's device is set to dark
mode those values take over and the site becomes a night-garden version of
itself. **A colour added to one block must be added to the other**, or dark mode
breaks.

The rest of the file is grouped by section with `── header ──` style comments,
in the same order as the HTML.

**The one CSS idea worth knowing:** `.ph` is a shape, not a picture. It sets the
aspect ratio and draws a green cross-hatch in CSS gradients, and the real
`<img>` carries the same class — so the box is the right size before the photo
arrives and nothing on the page jumps when it lands.

### `code/script.js` — the behaviour

Numbered sections. No libraries — every one of these is built into the browser,
which is why the whole site is under 80 KB of code and loads instantly.

> Note: the sections run 1–14, but **§12 sits last in the file, after §14.**
> Navigate by searching for the `── n. name ──` banner rather than by scrolling
> to where a number ought to be.

**1–3. The data.** Three lists at the top, and the only things you edit for a
normal content change:

- `CAFE` — phone number, opening and closing time, bookable hours.
- `MENU` — the menu, shaped `Tab → Course → [dish, price, 'v'/'n', 'pick'?]`.
  Add a dish by adding one line. You never touch `index.html`.
- `REVIEWS` — the quotes in the carousel.

**4. The clock.** Reads the time **in Hyderabad**, not on the visitor's device,
so it stays correct for someone browsing from another timezone. It drives three
things: the open/closed pill in the header, the arrow marking today's row in the
opening-hours table, and the time of day the hero is painted in.

**5. The canopy.** One `<canvas>`, pinned to the viewport behind the **whole
page** — not per section. It sits at `z-index: 0` and everything else is lifted
to `z-index: 1`, which is why sections are left transparent on purpose.
**Give a section a solid background and you cover the leaves.** Three layers:

- *Light* — soft blobs drifting at about a pixel a second, the way sun moves
  through leaves. Their colour comes from the `--wash-*` variables in
  `code/styles.css`, which change with the hour: cool green at 11am, gold at
  4pm, amber at dusk, deep canopy after eight. The same page looks different in
  the morning and at night.
- *Glow* — a warm pool of light that follows the cursor a few frames behind.
- *Leaves* — they fall slowly and sway. Move the cursor near one and it scatters
  away; flick across and they get carried along, then settle back into the
  drift. The push is a force with damping, not a position, which is why nothing
  snaps or jitters.

Three things keep it cheap:

- The loop **stops** when the tab goes to the background. An animation nobody is
  looking at is what drains a phone battery.
- It draws one still frame and never starts the loop for anyone who has
  "reduce motion" switched on.
- Leaf count drops from 34 to 18 on narrow screens.

One mobile detail worth knowing: scrolling on a phone collapses the address bar,
which fires a `resize` event. Re-seeding there would re-scatter every leaf
mid-scroll, so the handler only starts over when the **width** actually changes.

The numbers worth adjusting, all in `seed()` and just above it: `REACH` (how far
the cursor's push carries, currently 190px), the leaf counts, and the two
opacity values in `draw()` — `0.18` and `0.24`. Raise those and the leaves get
bolder; much past `0.3` and body text starts to fight them.

**6. Chrome.** The mobile hamburger, the hairline that appears under the header
once you scroll, and the scroll-spy that underlines the nav link for the section
you are passing.

**7. Reveal.** Sections lift into place as they come into view
(`IntersectionObserver`), and the rating and review-count figures count up once.
Written so that if JavaScript fails entirely, everything is simply visible —
never a blank page.

**8. The menu board.** Top tabs (Food / Drinks / Sweet), then a course filter
underneath. Rendered from `MENU`, with veg and non-veg markers and a "Pick"
badge on the house favourites.

**9. The lightbox.** Click a photo → fullscreen. Arrow buttons, left/right keys,
Esc to close, click the backdrop to close, and focus returns to the photo you
came from.

**10. The reviews carousel.** Auto-advances every six seconds, pauses on hover
or keyboard focus, dots and arrows to steer.

**11. Booking.** The form builds a WhatsApp message and hands it over. See
section 2 for why there is no server behind it.

**One thing worth knowing about dates.** `toLocaleDateString` writes
"12 Sept 2026" on some phones and "Sep 12, 2026" on others. A booking message
whose wording changes with the customer's device locale is a support problem
waiting to happen, so the date is spelled out by hand from two small arrays
instead. Keep it that way.

**12. Self-check.** Open the page with `?selftest` on the end of the address and
press F12 → Console. It runs 23 checks — opening-hours boundaries (09:59 closed,
10:00 open, 22:59 open, 23:00 closed), which light each hour maps to, time and
date formatting, and that the booking message carries every field. **If you
change the hours or the message, run this before you ship.**

**13. Splash.** The pointer nudges the splash photo behind the OTC letters on
the first screen. Two custom properties running -1 to 1; the CSS does the
moving. A touch screen never fires `pointermove`, so phones get a still frame
for free.

**14. Events.** Anything worth counting carries `data-ev` in the HTML —
`call_click`, `whatsapp_click`, `menu_view`, `book_click`, `instagram_click`,
`booking_submit`. One delegated click listener catches all of them and hands the
name to `track()`, which is currently a no-op stub. Wiring up an analytics tool
means uncommenting one line inside it.

Directions cannot be counted here: the map is a Google iframe, and a
cross-origin frame will not report its own clicks. That number lives in the
Google Business Profile dashboard.

**Photos are plain HTML.** Each one is
`<img class="ph" src="images/garden.jpeg" loading="lazy" alt="…">` written
straight into `index.html`, so the browser handles lazy-loading properly. To
change a photo, change the `src`. To change its description, change the `alt`.

*(An earlier version guessed the file extension at runtime via `new Image()`,
which downloaded every photo up front and defeated the `loading="lazy"` it set
afterwards, leaving a 404 in the console for every miss. Don't reintroduce it.)*

### Why each interaction is there

| Interaction | Why it earns its place |
|---|---|
| Interactive canopy | The cafe's identity is light through leaves. Leaves that scatter from the cursor make the first screen something you play with, not just look at. |
| Time-of-day light | The page at noon and the page at nine are visibly different. |
| Open/closed pill | Answers the single most common question before anyone has to ask it. |
| Scroll-spy nav | Tells a long page where you are. |
| Scroll reveal | Paces a long page. Subtle — 16px and 0.7s, not a bounce. |
| Count-up on the rating | Draws the eye to the strongest number on the page. |
| Tabbed menu | 40+ dishes without a wall of text. |
| Lightbox | Photos are the product. Let people look properly. |
| Reviews carousel | Social proof that fits in one screen. |
| Booking composer | Turns a browse into a message the cafe can act on. |

Nothing spins, bounces or follows the cursor. That restraint is deliberate.

### `build.sh`, `demo.html`, `artifact.html`

Optional. `build.sh` glues the three files into one self-contained `demo.html`
you can email or open from a USB stick with no folder around it.
`artifact.html` is the same page with the outer `<html>`/`<head>`/`<body>`
wrapper removed, for embedding. Regular hosting needs neither — you upload the
folder and it works.

```bash
bash code/build.sh
```

Both outputs are **generated**. Edit the three sources, never the generated
files — a rebuild overwrites them.

## 2. About databases — why there isn't one

**A cafe website does not need a database.**

A database is for information that changes without a developer touching it. A
social network needs one because millions of people post every second. An online
store needs one because stock counts drop with every sale.

A cafe's website has a name, an address, opening hours, a menu and some photos.
That changes a few times a year, and when it does, someone edits a file and
re-uploads it. Storing it in a database means paying for a server every month so
it can hand back the same answer it gave yesterday.

### Static vs dynamic

| | **Static** (this site) | **Dynamic** (with a database) |
|---|---|---|
| How it works | Files sit on a server, sent as-is | Server builds the page fresh each visit |
| Speed | Instant | Slower — has to query and assemble |
| Running cost | None | A monthly server bill |
| Attack surface | Almost nothing to attack | The usual target |
| Breaks if ignored | Never | Yes — needs updates and backups |
| Change the menu | Edit one line, re-upload | Log into an admin panel |

### The booking form

The booking section behaves like any restaurant reservation form — date picker,
guest stepper, time-slot pills, seating choice, validation — right up to the
last step. Then, instead of posting to a server, it writes the booking out as a
message:

```
Hi Old Tree Cafe, I would like to book a table.

Name: …
Date: …
Time: …
Guests: …
Seating: …
```

…and opens WhatsApp with it already typed.

This is deliberate. A server-backed booking system needs something to receive
the form, a database to store it, an email service to notify the cafe, an admin
panel for staff, and someone whose job it is to check that panel. All of it
costs money every month and only works if a staff member remembers to log in.

The cafe already has WhatsApp open all day. The booking arrives where somebody
is definitely looking, they reply to confirm in one line, and the customer keeps
the confirmation in a thread they can find again. Nothing to maintain, break or
leak.

No visitor data is stored, transmitted or tracked anywhere. The form's contents
go into a WhatsApp link and nowhere else.

### When a database *would* be justified

- **Online ordering with payment** — needs orders, payment records, order status.
- **Real capacity-aware booking** — needs to know which slots are gone.
- **A loyalty programme** — needs a record per customer.
- **A blog or events page the owner edits themselves** — this one still doesn't
  need a database; a CMS like Netlify CMS or Sanity gives an edit screen on top
  of static files.

## 3. Putting it online

Any static host works. Netlify, Cloudflare Pages, Vercel and GitHub Pages all
serve this for free.

The manual route, for a host with drag-and-drop:

1. Sign up.
2. Choose deploy manually / drag-and-drop.
3. Drag the project folder onto the page.
4. A live link appears immediately.

Upload `index.html`, `robots.txt`, `sitemap.xml`, `code/` and `images/` — the
whole folder as it stands. HTTPS certificates are issued automatically by every
host listed above; that is where the padlock in the address bar comes from.

### The domain

Three places carry the site's address, and all three are currently written as
`https://oldtreecafe.com`. **If the site is served from any other address,
change all three** or search engines will index the wrong one:

| Where | What |
|---|---|
| `index.html` `<head>` | `canonical`, `og:url`, `og:image` |
| `index.html` JSON-LD | `@id`, `url`, `image`, `logo`, `menu` |
| `robots.txt` | the `Sitemap:` line |
| `sitemap.xml` | `<loc>` |

A mismatched `og:image` is the usual cause of a blank preview card when the link
is pasted into a chat.

### After it is live

- Submit `sitemap.xml` in **Google Search Console** and confirm the page is
  indexed. Run the `<head>` through the
  [rich results test](https://search.google.com/test/rich-results) — it should
  come back as a Restaurant with hours, address and phone.
- Paste the live URL into a chat with yourself and check the preview card
  renders.
- Claim the **Google Business Profile** and put the website link in it. For a
  local cafe this is worth more than everything else combined — it is what
  appears in Google Maps. The name on the profile and the name on the site
  should match word for word.
- Put the link in the Instagram bio.

## 4. Quick edits

| To change | Open | Look for |
|---|---|---|
| A dish or price | `code/script.js` | the `MENU` list, §2 |
| A review | `code/script.js` | the `REVIEWS` list, §3 |
| Phone number | `code/script.js` **and** `index.html` | see below |
| Bookable time slots | `code/script.js` | `CAFE.firstSlot` / `lastSlot` |
| Opening hours | `code/script.js` **and** `index.html` | `openMinute` / the hours table |
| The colours | `code/styles.css` | the `:root` block, §1 |
| The time-of-day light | `code/styles.css` | the `--wash-*` phases, §3 |
| Headline or any text | `index.html` | the `══ SECTION ══` comments |
| An FAQ answer | `index.html` | the `<details>` list in the Visit section |
| A photo, or its alt text | `index.html` | the `src` / `alt` on that `<img class="ph">` |

Two of those are deliberately duplicated, so change every copy together:

- **The phone number appears in six places** — `CAFE.phone` in `code/script.js`,
  and in `index.html` the JSON-LD `telephone` plus four `tel:` links. If they
  disagree, the booking button and the structured data point at different
  numbers.
- **The opening hours appear in two forms** — minute numbers in
  `CAFE.openMinute` / `closeMinute`, and readable text in the `index.html` hours
  table and its `openingHoursSpecification`. The code needs numbers, the table
  needs words. After changing either, open the page with `?selftest` and confirm
  all 23 checks pass.
